## Templates

`ms-proteomics v1.1.0`, `vertebrates v1.1.0`, `single-cell v1.0.0`.

**`vertebrates`, not `human` — forced, and the screen's "MIXED organism" warning is real.** PRIDE
lists both *Homo sapiens* and *Xenopus laevis*, and both are genuinely present (53 HeLa rows,
30 Xenopus rows). I computed the **symmetric closure** of `mutually_exclusive_with` across all
template YAMLs (the graph is asymmetric per CLAUDE.md; here `human`↔`vertebrates` happens to be
declared in both directions): `human` excludes `vertebrates`. Only one organism template may be
declared. `vertebrates` covers both (human *is* a vertebrate); `human` would have been illegal for
30 rows.

**Cost of that choice:** `characteristics[age]` and `characteristics[ancestry category]` are
licensed only by `human`/`cell-lines` and are therefore **unavailable**, so HeLa S3's donor
demographics (Cellosaurus `AG=30Y6M`, `Population: African American`) cannot be recorded here.
`sex` survives — `vertebrates` licenses it.

### `cell-lines` was NOT declared — the #35 B1 trap, confirmed

`characteristics[cell line]` is `required` in `cell-lines/1.1.0` with **both** `allow_not_available`
and `allow_not_applicable` = `false`. The 30 Xenopus rows have no cell line and **no legal value
exists for them**. Declaring `cell-lines` would mean asserting a cell line for 30 embryo rows, or
discarding the study's entire biological demonstration. Same resolution as `PXD019515` and
`PXD031955`, reached independently.

Consequence: `characteristics[cellosaurus accession]` is unlicensed, so **`CVCL_0058` is not
recoverable from this file as a dedicated column**. Mitigated via `cell type` (below).

### ⚠ `dia-acquisition` was NOT declared — a second instance of the same trap, and this one is new

This is worth an upstream issue. `dia-acquisition/1.1.0` owns
`comment[proteomics data acquisition method]` as `required`, `allow_not_available: false`,
`allow_not_applicable: false`, with a `values` validator of **exactly** `["Data-independent

`ms-proteomics` licenses `comment[proteomics data acquisition method]` with a permissive PRIDE

Every one of the 44 columns was checked against the resolved 80-column union

## 🔴 The deposition contains 8 byte-identical duplicate files (83 files = 75 runs)

sampled offset.**

**Why**, established from the deposited `.msf` files (not guessed): the submitter's own input paths
are `E:\...\Official Data for PRIDE Submission\Gradiant Separation Time\DDA\RAW\30 min\...`. The
same acquisition served two figure panels, so it was copied into two folders and flattened into one
PRIDE directory under two names. `DDA_350-900_combined.msf` and `90min_HeLa_DDA_combinednormalized.msf`
**take the same three raw files as input** — i.e. the "350–900 m/z" optimisation *is* the 90-min DDA
condition. The DIA `10X40win` / `60min` pairs are the same story.

**The last row is a genuine data-integrity defect, not just redundancy:**
`HelaDIA40mintrial2` and `Hela**V**DIA40mintrial3` are the same acquisition deposited as *trial 2*
and *trial 3*. The 40-min DIA group therefore looks like 5 technical replicates but contains only
**4 distinct measurements**. The paper says "3–5 technical replicates" per condition. A reviewer
should treat any n=5 claim for that condition with suspicion.

**`parse_sdrf` independently rediscovered this.** My first build gave both members of a pair the
same `assay name` (they are one run), and the validator rejected it: `Combination '(source name,
assay name, comment[label])' is duplicated`. SDRF structurally cannot express "two files, one run,
one sample" — every row needs its own assay identity.

**Resolution (a judgement call — attack this one):** I annotate **all 83 deposited files**, because
the SDRF is an index of the deposition and `comment[data file]` should resolve every file in it;
the brief permits excluding a run only for the `cell line` trap. Each deposited file gets a
distinct `assay name` derived from *its own* filename token and matching the PD analysis it fed
(`HeLa_10ng_DDA_90min_tr1` vs `HeLa_10ng_DDA_mz350-900_tr1`). The pairs are then detectable because
they share `source name` and every technical value. **A consumer that processes all 83 files without
reading this section will double-count 8 runs.** The alternative — 75 rows — is scientifically
cleaner but leaves 8 deposited files unresolvable. I chose the loud error over the silent one, and
the table above is the deduplication key.

## Key decisions and evidence

**Instrument — the artifact contradicts PRIDE, confirmed by three independent sources.** PRIDE's
`instruments` field says **`Q Exactive`**. It is wrong. The paper says "Q-Exactive Plus"; HTTP-range
reading the first 256 KB of **all 83** raw files and decoding utf-16-le returns `Q Exactive Plus` in
**83/83**; and the deposited `.msf` files record `Q Exactive Plus Orbitrap` for every input.
Annotated `MS:1002634`. `MS:1002523` ("Q Exactive") would have passed validation cleanly. Identical
to the error PRIDE carries for the sibling `PXD031955` from the same lab.

**🔑 DDA/DIA cannot be read off the filenames — the raw headers overturn them.** The naming is
internally inconsistent:

- `2021-1-20-BS03-Hela-**60min**-trial1.RAW` → **DIA** (no "DIA" token in the name)
- `2021_2_10_BS01_Hela-**30min**trial3.RAW` → **DDA** (no "DDA" token either)

A filename rule of "contains DIA ⇒ DIA" misclassifies the entire 5-run 60-min DIA set. I classified
every run from its embedded Xcalibur method instead — DDA runs carry `Isolation window 1.5 m/z` +
`dd-MS2` + scan range `350–900`; DIA runs carry `Isolation window 10.0`/`20.0 m/z` + `MSX count` +
scan range `490–910`. The six distinct method files partition the 83 runs exactly:

| Xcalibur method | runs | arm |
|---|---|---|
| `...Hela_DDA_350-900.meth` | 21 | HeLa DDA |
| `...Hela_DIA_500-900 10X40 AGC3e6.meth` | 22 | HeLa DIA 10 ng |
| `DIA window\...10X40 AGC3e6.meth` | 16 | Xenopus quasi-cellular |
| `Single cell mesurements\...for single cell.meth` | 14 | Xenopus subcellular |
| `For CE-DIA single HeLa measurements\2022-12-7...20X20 for single cell.meth` | 5 | HeLa 200 pg, 20×20 |
| `For CE-DIA single HeLa measurements\2023_1_4...10X40 for single cell.meth` | 5 | HeLa 200 pg, 10×40 |

The build script **asserts** the filename-derived arm against the raw-header method for all 83 rows
and fails loudly on mismatch. The `.msf` input lists corroborate independently: PD's own file paths
say `Gradiant Separation Time\DDA\RAW\30 min\2021_2_8_BS05_Hela digest-30min trial1.RAW` — the
submitter renamed files on deposition, so the `.msf` names do **not** match the deposited names, and
only the date+`BS##` token joins them.

**🔑 There are TWO Xenopus arms, not one. The screen row and the task brief both describe only one.**
The brief says "Subcellular proteome aspirated". That is true of 14 runs. The other 16 are a
different experiment, which I found because a deposited DIA-NN report is named `Entire_D11_report`:

> "we also analyzed the **entire intracellular proteome** from N = 5 different D11 cells using a
> microcapillary (Figure 4B), **excluding the outer membrane of the cells**. We expected these
> **quasi-cellular aspirates** to reflect information on cell cycle and embryo variability."

So: `subcellualr_DIA_report.pg_matrix.tsv` (14 runs, 2021-06, embryos E1–E5) = the ~10 nL / ~11 %
aspirates — the paper's headline. `Entire_D11_report.pg_matrix.tsv` (2023-06, cells 1–5) = whole
intracellular content. **These are ten different cells from ten different embryos two years apart**,
not one arm; they are given separate source names and separate cell identifiers. Collapsing them
would assert a cell identity that does not exist.

The report row counts pin the arms to the paper's numbers: `subcellualr` = **1241** protein groups
↔ abstract "quantify **1242** proteins in subcellular niches"; `20X20_200pgHeLa` = **1161** ↔
abstract "identified **1161** proteins ... from single HeLa-cell-equivalent (~200 pg)".

**🔑 The HeLa standard is HeLa S3, and the paper gives the part number.** Methods: "The HeLa proteome
digest standard was supplied by Thermo Fisher (**part no. 88329**, Pierce)". The vendor page for
88329 states the digest "stammt von einer gut etablierten **HeLa S3**-Referenzzellinie eines
Adenokarzinoms" — HeLa **S3**, not parental HeLa. Exactly the brief's trap. Verified against the
live Cellosaurus API: `CVCL_0058` = HeLa S3, `HI CVCL_0030 ! HeLa` (a clone *of* parental HeLa),
`Derived from site: Uterus, cervix; UBERON=UBERON_0000002`, `SX Female`, `Cancer cell line`.
`EFO:0002791` = `HeLa-S3` confirmed live. Annotating `CVCL_0030`/`EFO:0001185` here would have been
validator-clean and wrong.

**HeLa S3 identity is preserved via CLO, since `cell-lines` is undeclarable.** `characteristics[cell
type]`'s resolved validator explicitly allows **`clo`** alongside `cl`/`bto`; CLO contains nothing
but cell lines. HeLa rows carry `NT=HeLa S3 cell;AC=CLO:0003696`. This follows `PXD019515`'s
precedent (which used `CLO:0003684`, parental HeLa — correct *there*, wrong here).

term API). I picked `CLO:0003696` because its label matches the vendor's own "HeLa S3" spelling.
This is arbitrary and is a genuine CLO defect worth an upstream issue.

**🔑 Modifications — PRIDE's protocol text is demonstrably FALSE, and its `modifications` field is
right.** The two PRIDE fields contradict each other:

- `data_processing_protocol`: *"In this project, static and dynamic modifications were **excluded**
  during searches."*
- `modifications`: `["monohydroxylated residue", "iodoacetamide derivatized residue"]` (= Oxidation
  + Carbamidomethyl)

I resolved this from the **deposited search outputs**, per the brief's precedence rule. I read the
Proteome Discoverer `.msf` files **without downloading them** — they are SQLite, so I wrote a
minimal SQLite-over-HTTP-range reader (schema walk + B-tree traversal + overflow-page handling,
~19 page reads for a 643 MB file) and pulled the workflow XML. **All five** `.msf` files agree:

```
Precursor Mass Tolerance = 10 ppm      Fragment Mass Tolerance = 0.02 Da
1. Static Modification   = Carbamidomethyl / AminoAcids="C"
1. Dynamic Modification  = Oxidation / AminoAcids="M"
Enzyme = Trypsin (CleavageSites KR)    Max. Missed Cleavage Sites = 2
Target FDR (Strict) = 0.01             DB = 2021_HeLa_uniprot-proteome_UP000005640+reviewed_yes.fasta
```

Carbamidomethyl and Oxidation **were** searched. Corroborated independently by the Spectronaut
`.sne` files, whose library-based DIA peptides are littered with `C[Carbamidomethyl (C)]` and which
name their library `CE 350-900 library 7 runs 20kV` — matching the paper's "spectral library was
developed by analyzing the HeLa proteome digest using DDA in **7 technical replicates**".

The submitter's sentence is a **Xenopus-arm statement over-generalised to "this project"**. And it
is chemically coherent that way: the commercial Pierce standard is vendor-digested (and alkylated),
while the Xenopus workflow explicitly eliminates alkylation. So:

- **53 HeLa rows** → `NT=Carbamidomethyl;AC=UNIMOD:4;TA=C;MT=Fixed` + `NT=Oxidation;AC=UNIMOD:35;TA=M;MT=Variable`
- **30 Xenopus rows** → both `not applicable`

This is the brief's "never assert Carbamidomethyl without an alkylation step" warning meeting its
mirror image: here refusing Carbamidomethyl on the HeLa rows would have been the error, and the
alkylation step is the vendor's. UNIMOD:4/UNIMOD:35 verified live; no UNIMOD:1/UNIMOD:21 swap
(neither Acetyl nor Phospho appears anywhere in this dataset).

**Xenopus modifications = `not applicable`, not `not available`.** Methods: "The conventional
bottom-up proteomics steps of protein **reduction and alkylation were eliminated** to minimize
sample loss". No alkylation ⇒ Carbamidomethyl cannot exist in the sample. The value is not missing,
it is absent by design. Matches sibling `PXD031955`'s Xenopus CE rows exactly.

**🔑 Cleavage agents differ per arm, and the vendor is the source for one of them.** The paper's
"Proteins were digested with MS-grade TPCK-modified trypsin" describes the **Xenopus** prep only
("digestion to peptides, with the addition of 1 µL of 0.25 µg/µL trypsin"). The HeLa digest is
**bought pre-digested**, and the vendor page for 88329 states it is "**Hergestellt mit LysC und
Trypsin**" (prepared with LysC and Trypsin).

- HeLa rows → `NT=Trypsin;AC=MS:1001251` + `NT=Lys-C;AC=MS:1001309`
- Xenopus rows → `NT=Trypsin;AC=MS:1001251` + `not applicable`

Note the deliberate mismatch with the search: PD's `Enzyme Name` is **Trypsin only**. The column is
defined as "Enzyme or chemical used for protein **digestion**", not the search setting, so the
vendor's actual chemistry wins. **This is an inference from a vendor page, flagged for review.**

**Collision energy — the raw bytes contradict the paper on exactly 14 rows.** The paper states one
value: "dissociated ... at **28%** normalized collision energy (NCE) in the HCD cell", for both
modalities. The raw headers say `nce: 28` for 69 runs but **`nce: 27` for all 14 D11 subcellular
runs** (the `...for single cell.meth` method). Raw data > Methods prose, so those 14 rows carry
`27 NCE`. Small, but it is a real per-arm discrepancy that only the headers expose.

**Tolerances are split by evidence, not assumed.** `10 ppm` / `0.02 Da` on the **21 DDA rows** —
proven, from the deposited PD workflow. **`not available` on the 62 DIA rows**: those were searched
with DIA-NN 1.8.1 library-free (per PRIDE) or Spectronaut, no settings file is deposited, the SI is
unreachable, and DIA-NN infers mass tolerances automatically. Copying `10 ppm`/`0.02 Da` across
would have been fabrication. (The sibling `PXD031955` legitimately used 10 ppm/0.02 Da — its paper
states them; this one's does not.)

**`developmental stage` = `cleavage stage` (UBERON:0000107) for Xenopus** — stated: "cultured to the
**16-cell stage**" (= stage 5). The term resolves within EFO, which the column's validator requires.
Verified.

**Anatomy/identity for Xenopus:** `organism part` = `embryo` (UBERON:0000922) — the cell is *in the

## Replicate structure

- **HeLa**: one commercial standard ⇒ `biological replicate = 1` throughout, `pooled sample =
  pooled` (a bulk culture digest — many cells, sources unknown). `technical replicate` = the trial
  index within each condition, i.e. the submitter's own `trialN` token, which the `.msf` input lists
  confirm. The 200 pg trials carry no token and were numbered 1–5 by acquisition date.
- **Xenopus**: `biological replicate` = the embryo index (1–5) in **each** arm — the paper states
  "Each experiment was repeated N = 5 times using **different embryos** (biological replicates),
  with each proteome sample analyzed in 3 technical replicates". `pooled sample = not pooled`.
- Deposition vs that claim: the subcellular arm has **14** runs, not 15 (E1 has only 2 reps); the
  quasi-cellular arm has **16**, not 15 (cell 3 has a 4th rep on 2023-06-17, and cell 3's rep 2 is
  **deposited but absent from `Entire_D11_report`** — 15 of 16 runs in that report). Both are
  recorded faithfully rather than forced to the paper's round numbers.
- `fraction identifier = 1` and no fractionation anywhere.

**`single cell isolation protocol = not applicable` on every row — and I want this attacked.** The
column is `required` with `allow_not_available: false` / `allow_not_applicable: true` (the

The fixed enum is FACS / cellenONE / microfluidics / LCM / manual picking / nanoPOTS / droplet

- **Xenopus (30)**: **no cell is isolated either, in either arm.** The blastomere stays in the live
