# PXD041328 — annotation report

**Status: BLOCKED (not annotatable).** Multiplexed TMTpro single-cell proteomics with **no deposited
channel → sample-identity map**. No SDRF TSV was produced. Fabricating channel or germ-layer
identities is forbidden by the annotator brief and would misrepresent every row.

## Study & publication

- **Title:** *Deciphering lineage specification during early embryogenesis in mouse gastruloids using
  multilayered proteomics.* Stelloo et al., **Cell Stem Cell** 2024.
- **PMID:** 38754429 · **DOI:** 10.1016/j.stem.2024.04.017 · **PMCID:** none.
- **Open access:** hybrid/CC-BY per Unpaywall, but **no OA full text is retrievable**:
  `get_pdf_by_unpaywall` returned `No PDF URL found (Unpaywall and Europe PMC)`; cell.com and
  ScienceDirect return HTTP 403; no PMCID means no Europe PMC `supplementaryFiles` endpoint.
- This PXD is the **single-cell proteomics (SCP) validation arm** — mouse gastruloid germ-layer cells,
  cellenONE-sorted into proteoCHIP nanowells, TMTpro-labeled, DDA on an Orbitrap Eclipse.

## Organism (verified, but moot given the block)

`Mus musculus` — PRIDE `organism = Mus musculus (mouse)`; confirmed against paper (mouse gastruloids).
NCBITaxon:10090. Had this been annotatable it would use the **vertebrates** template (not human), plus
`ms-proteomics` + `single-cell`. Species is not the blocker.

## The blocker — no channel→sample map (authoritative, from the deposited PD data)

I range-read the ZIP64 central directory of `SEARCH.zip` (no bulk download) and inflated the two small
design-bearing members. Both agree, and per precedence (raw/deposited data > paper > PRIDE fields) they
are authoritative:

**1. `SEARCH/CVG_Exp55.pdStudy` (PD study-design XML, 3.8 MB inflated).**
- **1350 `<Sample>` entries = 75 files × 18 TMTpro channels** (126, 127N, 127C, 128N, 128C, 129N,
  129C, 130N, 130C, 131N, 131C, 132N, 132C, 133N, 133C, 134N, 134C, 135N → **TMTpro-18**).
- **Every one of the 1350 has `SampleType="Sample"`.** None is marked carrier, booster, empty, or blank.
- Each sample `Name` is literally `<rawfile> - [<TMTtag>]` — i.e. the channel identity **is** the TMT
  tag, nothing biological.
- The **only** `Factor` is `"Experiments"` with options `Exp55`/`Exp56` (a batch label). Sample grouping
  (`SampleGroup`) is purely by `Quan Channel`. **No germ-layer, no cell type, no carrier/single-cell
  distinction anywhere.**

**2. `SEARCH/..._PeptideGroups.txt` (PD result table, header inflated from the deflate stream).**
- 2724 columns; the abundance columns are `Abundance F{n} {TMTtag} Sample Exp{55|56}` — i.e. every
  channel is the generic **`Sample`** label. This is the canonical Proteome Discoverer *no-map* state
  (equivalent to `"Sample, n/a"`), exactly the case the brief flags as BLOCKED.

The 50 GB `.msf` SQLite was **not** fully extracted (impractical), but it is the store the `.pdStudy`
and `PeptideGroups.txt` are built from; its sample layout is the same design shown above. No further
identity is recoverable from it.

**Consequence:** I cannot assign a sample identity to **any** row — not even which channel is the
carrier vs a single cell, let alone which single cell is ectoderm/mesoderm/endoderm. The paper's
abstract confirms germ-layer SCP validation, but the germ-layer → channel assignment "must come from a
deposited map, not inferred," and **none exists in the deposition**. No partial annotation is possible,
because no channel in any file has a recoverable identity.

## What would unblock

A deposited **per-(file × channel) sample map** — e.g. a proteoCHIP well/channel layout table stating
which TMT channel is the carrier vs which single germ-layer (ecto/meso/endoderm) cell — as a Cell Stem
Cell supplementary table (`mmc*`), a cellenONE isolation sheet in `files/all`, or a re-deposited PD
study with real sample names replacing the generic `Sample` default. Given such a map, the 1350 rows
(minus carrier/empty channels) are straightforward to build (TMTpro-18, vertebrates + ms-proteomics +
single-cell templates).
