## The annotatability question (this is a carrier-TMT dataset — the PXD043473 failure mode)

**Not blocked. The channel → sample map is deposited.** Every SCP result table carries the
per-channel annotation in its own column headers, e.g.

```
Abundance: F74: 126, Sample, R1, Control     Abundance: F74: 131, Sample, R1, CP
F1 126 CP Control R1                         Abundance F1 130N Empty R1
```

This is the exact opposite of PXD043473, where Proteome Discoverer had left every channel as the
default `"Sample, n/a"`. Here the submitters named the channels, so `Control` / `Treated` / `CP` /
`CP Control` / `CP Treated` / `Empty` / `DMSO` / `Attached` / `Detached` / `MTX alive` … are all
recorded per set.

**The layout is not uniform, so the map is load-bearing.** Set R1 has `126 = Control`; set R10 has
`126 = Treated`. The interspacing flips between sets. Assuming a fixed layout — the obvious
shortcut — would have inverted case/control on roughly half of 2525 single cells and still passed
`parse_sdrf` cleanly.

### Proving set `R_n` ↔ raw file `Rxn_n`

The tables label sets `R1…R24`; the raw files are named `…_Rxn1…Rxn24.raw`. That correspondence is
an assumption, and a permutation would silently attach the right composition to the wrong file. It
is confirmed by a natural experiment in the deposit:

| | |
|---|---|
| `SCP_MTX_3h` raw files | 23, numbered `Rxn1–7, **Rxn9**–24` — **`Rxn8` is not deposited** |
| `SCP_MTX_3h` table | 23 sets, numbered `R1–7, **R9**–24` — **`R8` is absent** |

The table skips the same integer the file list skips. An independent or permuted labelling would
have produced a contiguous `R1…R23`. Every other group independently matches on set count
(24 sets ↔ 24 files, 16 ↔ 16, 8 ↔ 8, 3 ↔ 3, 2 ↔ 2).

Three further cross-checks land exactly, and none were engineered:

- `SCP_168SC_MTX_48h_split_CP` → 24 sets × 7 single-cell channels = **168** — the number in the filename.
- `Raw_peptide_intensities_test_64SC_8TMT_sets` → 8 sets × 8 = **64** — the number in the filename.
- Paper: *"A total of 96 single cells were sorted for each condition/drug"* → 24 sets × 4 control +
  4 treated = **96 + 96** per drug/timepoint. Matches every complete time-course group.

## Key decisions and evidence

**Which reagent per run — the screen said both "TMT" and "TMTpro".** Both are real, and they split by
run group, not by study:

| reagent | rows | mod written | groups |
|---|---|---|---|
| TMT10plex / TMT11plex | 2682 | `UNIMOD:737` (TMT6plex) | time course, splitCP, semi-bulk TMT10, test 64SC |
| TMTpro 16-plex | 355 | `UNIMOD:2016` (TMTpro) | TMTpro SCP, semi-bulk TMTpro, bulk |

Assigned from the channel range each deposited table actually uses (a `133C`/`134N` channel cannot be
TMT10plex) and corroborated by the paper (*"TMT10plex and TMT11plex including channel 131C were
used"*) and PRIDE (*"Both TMT10plex and 16-channel TMTpro were used"*). This is the swap
`tools/column_ontology_map.py` can never detect, since it maps both UNIMOD:354 and UNIMOD:737 to
TMT6plex; it was derived from evidence, not from the tool.

**The carrier is annotated as a distinct sample — 351 rows** (`sample type` = `carrier`
/ PRIDE:0000901, `cell identifier` = `carrier`, the spec's own special value). Omitting it is the
classic error. Carrier size is stated per design, not guessed:

| carrier | channels | cells/well | treatment | evidence |
|---|---|---|---|---|
| TMT10plex time course + test64 | `131` | 200 | **`not applicable`** | *"a single channel with CP (200 cells in channel 131)"*; the well is 100 treated **+** 100 control, so a single-valued treatment does not apply |
| TMTpro SCP | `126`, `127N` | 100 | DMSO / MTX | deposited: `126 CP Control`, `127N CP Treated` — explicit |
| splitCP TMT11plex | `131N`, `131C` | 100 | **`not available`** | see below |

The two reserved words are doing different work and are not interchangeable: the TMT10 carrier's
treatment *does not apply* (it is a 50/50 mixture); the splitCP carrier's treatment *exists but was
not provided*.

**The splitCP carrier conflict — 48 rows left `not available`.** The paper states the composition
unambiguously: *"the CP was split into two channels, 131N and 131C, one composed of 100 control cells
and the other of 100 treated cells."* One is control, one is treated. **No source says which.** The
deposited evidence actively contradicts itself:

| source | 131N | 131C | verdict |
|---|---|---|---|
| `…split_CP_peptides.xlsx` **Sheet3** | `CP treated` | `CP treated` | curated (it alone marks `130N/130C` as `Empty`, matching the paper) — but cannot be right, the paper says one is control |
| `…split_CP_peptides.xlsx` **Sheet1** | `Control` | `Sample` | generic alternating auto-naming; demonstrably wrong in the same channel range (calls the empty `130N/130C` `Control`/`Sample`) |

Sheet1 is the only source that names a control CP, and it is exactly the source proven unreliable
there. Rather than take a coin flip that would pass validation, both channels are annotated as
carriers (which they certainly are) with `treatment` = `not available`. **Unblocked by:** a channel
key from the authors.

**Cell viability.** `live` for all FACS-sorted single cells and carriers — the paper sorts
*"the collected attached **surviving** cells"* and the CP plate draws from the same population.
`dead` for the 50 `Detached` / `dead` bulk rows (*"Detached dying cells were also collected"*; the
bulk table's own headers say `MTX dead`). `not available` for the 30 semi-bulk TMT10 rows, whose
headers say only `Control`/`Treated` with no attached/detached qualifier.

**`RTX` = TDX.** The bulk table's channels are labelled `RTX alive` / `RTX dead`, a token that
appears in no other table and in neither protocol. Raltitrexed **is** tomudex (paper: *"tomudex
(TDX), also known as raltitrexed"*), so `RTX` rows carry `NT=Raltitrexed;AC=NCIT:C1804`, the same
term as TDX.

**Cell line.** A549 → `EFO:0001086` / `CVCL_0023` / `A-549`, donor 58Y male, European ancestry
(Cellosaurus `CC Population: Caucasian`). The OLS cell-line trap fired as advertised: BTO fuzzy's top
hit was **`A549-CR`** (a cisplatin-resistant derivative, BTO:0005816). `EFO:0001086` is the exact
label match.

**NCIT smart-mode trap.** `searchClasses(query="methotrexate", ontologyId="ncit")` returned exactly
one confident hit — **`High-dose Methotrexate/Rituximab Regimen` (NCIT:C201529)**, a chemotherapy
regimen, not the compound. Fuzzy mode surfaced the correct `Methotrexate` (NCIT:C642). `camptothecin`
similarly resolved to `Camptothecin Sodium` (NCIT:C2344) instead of `Camptothecin` (NCIT:C338). All
24 accessions written to the file were re-verified live against OLS by exact `obo_id` lookup.

**Instrument.** `Orbitrap Fusion Lumos` (MS:1002732), confirmed **from the raw file headers**
(HTTP-range first 256 KB, utf-16-le) across all six run families — not just from PRIDE and the paper,
which happen to agree here.

**Replicate structure.** Each single cell is a distinct biological replicate (numbered within its
drug × timepoint group). Carriers and bulk pools use `biological replicate` = `pooled` (legal:
`allow_pooled = true`). The 3 semi-bulk and 2 bulk runs are re-injections of one labelled TMT set, so
they share `source name` across runs and are distinguished by `comment[technical replicate]` — the
only 56 duplicated source names in the file, all intentional.

**Batch.** `comment[sample preparation batch]` carries the TMT set (e.g. `MTX_48h_R12`). The TMT set
is the batch the paper itself corrects for (SVA; Figure S1C, S4).

## Conflicts found and how they were resolved

1. **PRIDE `modifications` vs the paper.** PRIDE lists *"acetylated residue, deamidated residue,
   iodoacetamide derivatized residue"*. The paper's Data Analysis names exactly three variable
   mods: **Oxidation (M), Deamidation (N/Q), and TMT on K/N-term** — no Acetyl, no Carbamidomethyl.
   The peer-reviewed Methods were followed. (Iodoacetamide appears only in PRIDE's *bulk* prep
   text; the paper describes one search. Acetyl is unsupported by either protocol.) The SCP protocol
   has no reduction/alkylation step at all — freeze/thaw, 90 °C, trypsin.
2. **PRIDE bulk protocol vs the deposited bulk data.** PRIDE says bulk used *"1×10⁶ cells"* and
   *"TMT10plex"*; the deposited `bulk` table uses TMTpro channels up to `134N`, and the paper says
   *"about 500 cells per condition ... TMTpro-labeled (15-plex)"*. The deposited channel range is
   physical evidence and wins: bulk rows are TMTpro/`UNIMOD:2016`.
3. **Sheet1 vs Sheet3** of the splitCP workbook — see above; unresolved by design, 48 rows
   `not available`.
4. **PRIDE `instruments` vs paper vs raw headers** — all three agree here (Orbitrap Fusion Lumos).
   Verified from raw headers anyway; no conflict.

## Inferred vs stated

  instrument, tolerances, HCD 35%, cell counts per condition, A549 donor demographics.
- **Inferred (documented):** `R_n ↔ Rxn_n` (proven by the `Rxn8`/`R8` gap, not assumed);

## Incidental findings (for whoever revisits)

- **Two deposited files are byte-identical.** `SCP_168SC_MTX_48h_split_CP_peptides.xlsx` and
  `Inbuilt_bulk_MTX_48h_peptides.xlsx` share MD5 `b042c1d0e5af87d4dbe2cc9cdf5d19a1` (55 548 697 B).
  The same 24-set splitCP workbook is deposited twice under two different names.
- **`Inbuilt_bulk_CP_raw_abundances_TMTpro.xlsx` is a projection**, not a separate experiment: it is
  the 2 CP channels of the 16 TMTpro SCP sets. It corroborates `126 = CP Control`,
  `127N = CP Treated` independently.
- **The MCP `get_project_files` truncation (issue #32) would have been fatal here.** The deposit has
  346 files; the tool caps at 100. The v3 `files/all` REST endpoint was used throughout.
- **`SCP_TDX_24h` is deposited as `.csv`** while its eight siblings are `.xlsx` — same 218-column
  layout.
- **`TERMS.tsv` `values` prose lists `study sample`, which is not a class in the PRIDE ontology.**
  A spec/ontology drift worth an issue; it left 161 rows with no expressible `sample type`.
- Europe PMC returns `is_open_access: true` for PMC9260713 but its JATS body is **empty** (ACS
  deposits abstract-only XML), and Unpaywall's `url_for_pdf` is null. The Methods were recovered from
  the PMC HTML render. A pipeline trusting `get_full_text_article` alone would have concluded there
  were no Methods and mis-annotated the modifications and the carrier design.
