## The mixed-acquisition wall (why `dia-acquisition` is absent)

This deposition is **genuinely mixed**: 449 diaPASEF runs and 71 ddaPASEF runs. The screen's
`acquisition=both` is correct, and it is correct *per run*, not per dataset.

`dia-acquisition/1.1.0` defines `comment[proteomics data acquisition method]` as:

```yaml
requirement: required
allow_not_applicable: false
allow_not_available: false
validators:
  - validator_name: values
    params: {values: [Data-independent acquisition], error_level: error}
```

A DDA row is therefore **inexpressible** in any SDRF that declares `dia-acquisition` — no legal
value exists for it, including both reserved words. And `comment[dia method]`,
`comment[scan window lower/upper limit]` and `comment[isolation window width]` are licensed by
**`dia-acquisition` alone** (verified in `TERMS.tsv`: `usage=dia-acquisition` for all four).

So the spec forces an exclusive choice for a mixed-acquisition deposition:

| option | cost |
|---|---|
| declare `dia-acquisition` | drop all 71 DDA runs — 71 real samples silently vanish |
| omit `dia-acquisition` (**chosen**) | lose 4 DIA columns, all `recommended`, none `required` |

The brief's scope rule is explicit — annotate every deposited run that has a sample; exclusion is
permitted *only* where a required column forbids both reserved words for a **sample-less** run.
Dropping 71 sample-bearing runs to keep four recommended columns inverts that rule. Acquisition
truth is preserved per row via `comment[proteomics data acquisition method]` (DIA/DDA), so nothing
is *misstated* — only under-described.

**What is lost:** for the 449 DIA runs, `diaPASEF`, the 400–1200 m/z scan range and the **25 m/z**
isolation window width. These were *measured*, not guessed — extracted from `DIAParameters.txt`
inside the deposited `.d` folders (fixed 25 Th windows: 400–425, 425–450, …). They are recorded here
because the SDRF cannot hold them. A DIA-only companion file declaring `dia-acquisition` would
recover them for the 449 DIA runs at the cost of the 71 DDA rows. Recorded in `annotations/BLOCKED.md`.

## Key decisions and evidence

**Instrument: timsTOF Pro, not timsTOF SCP.** PRIDE says only `timsTOF`. The paper's Methods say
"modified ... (timsTOF Pro, Bruker Daltonik GmbH)", and the prototype it describes is what later
shipped as the timsTOF SCP — the paper even captions a "Schematic representation of Bruker timsTOF
SCP". Writing `timsTOF SCP` (`MS:1003231` exists) would be the plausible, validator-clean, wrong
answer. Settled by the raw headers, which outrank both: `GlobalMetadata.InstrumentName` in
`analysis.tdf` reads **`timsTOF pro`** (TIMS04 serial 1854399.55, TIMS05 …145) and **`TIMS TOF PP`**
(TIMS02/TIMS2 serial 1838271.25, the 2018 pre-production naming). All 520 runs → `timsTOF Pro`.
The prototype ion-source modification — the paper's central instrument claim, and the entire point of
`RAW_Standard_vs_Modified_timsTOF.zip` — has no representation in `comment[instrument]`.

**Cell line: parental HeLa, not HeLa-S3.** `EFO:0001185` / `CVCL_0030`. The HeLa-S3 trap does **not**
apply: no commercial HeLa digest standard is used anywhere. Every benchmark run is the authors' own
bulk culture — "For all benchmark experiments, purified peptides from bulk HeLa cells were used.
HeLa was cultured in Dulbecco's modified Eagle's medium…". OLS smart mode returned `HeLa` exactly;
`mode="fuzzy"` was run as required and returned HeLa-S3 / HeLa M / HEp-2 as neighbours — all rejected.

**Cell-cycle design decoded from filename tokens + Methods.** The tokens are undocumented in PRIDE:

| token | treatment (paper Methods) | `cell cycle phase` | cells |
|---|---|---|---|
| `TB` | thymidine 24 h → release 4.5 h → **thymidine** 13 h | `G1/S` | 41 |
| `NB` | thymidine 24 h → release 4.5 h → **nocodazole** 13 h | `G2/M` | 45 |
| `G2` | thymidine block, then **released 7 h** | `G2` | 52 |
| `G1` | nocodazole block, then **released 2.5 h** | `G1` | 93 |
| `UB` | none | `not determined` | 203 |

The release mapping (7 h → early G2 from the G1/S block; 2.5 h → early G1 from the G2/M block) is the
paper's own sentence read in order, and matches the four target stages it names: "G1, the G1/S
transition, G2, and the G2/M transition".

**`characteristics[treatment]` is an ontology column** (`values = NCIT, EFO`), not free text — so the
protocol detail above cannot live in it. It carries the operative arresting drug only:
`Nocodazole` `NCIT:C75228`, `Thymidine` `NCIT:C880`. Note that `TB`/`NB` cells received *both* drugs
sequentially; the column has no `cardinality: multiple`, so only the arresting agent is stated and
the thymidine pre-synchronization of the `NB` arm is not representable. The template's own guidance
("Use 'untreated' for controls") is **unusable**: no generic `untreated` term exists in NCIT — the
fuzzy search returns only disease-specific terms ("Untreated Childhood Pineoblastoma"). Untreated
rows use `not applicable`.

**Modifications — the paper is wrong and the deposited search files are right.** PRIDE's
`modifications` field says "No PTMs are included in the dataset". The paper's Methods say cysteine
carbamidomethylation was fixed for the dilution series *and the cell count experiment*. The deposited
search parameters contradict the paper for two of four groups:

| group | evidence file | fixed | variable |
|---|---|---|---|
| 434 single cells | `MSFRAGGER_Output/fragger.params` → **`add_C_cysteine = 0.000000`** | none | `15.994900 M`, `42.010600 [^` |
| fractions + cell counts (48) | `MQ_Dilutions_SingleCells_*/summary.txt` → **`Fixed modifications` empty** for all 51 runs | none | Oxidation (M); Acetyl (Protein N-term) |
| bulk dilution (12) | `MQ_HeLaBulkDilution/summary.txt` | **Carbamidomethyl (C)** | Oxidation (M); Acetyl (Protein N-term) |
| standard vs modified (2) | `MQ_Standard_vs_ModifiedTimsTOF/summary.txt` | **Carbamidomethyl (C)** | Oxidation (M); Acetyl (Protein N-term) |

For the single cells this is *also* chemically right: the single-cell protocol lyses into 20% ACN /
100 mM Tris with **no reduction or alkylation step**, so there are no carbamidomethylated cysteines
to search — whereas the bulk protocol boils in PreOmics buffer "to denature, reduce, and alkylate
cysteins". Chemistry and the deposited `fragger.params` agree.

For the **48 fraction + cell-count runs the two disagree**: the fractions are alkylated bulk HeLa,
yet the deposited MaxQuant run searched them with no fixed modification. The SDRF documents the
analysis that was actually performed and deposited, so it follows `summary.txt`. Flagged as a likely
error in the authors' own search, not resolved here.

`UNIMOD:1 = Acetyl` (`PP=Protein N-term`, never `TA=`) and `UNIMOD:35 = Oxidation` verified live;
`UNIMOD:4 = Carbamidomethyl`. No swap.

**Cleavage agents.** `Trypsin` (`MS:1001251`) + `Lys-C` (`MS:1001309`) on all 515 rows. Bulk: "adding
lysC and trypsin in a 1:50 ratio"; single cells: "1 ng trypsin/lysC mix". Both searches specified
tryptic (`Trypsin/P` in MaxQuant, `stricttrypsin` in MSFragger) — but this column describes
digestion, and both groups used the two-enzyme mix.

**Fragment mass tolerance = 40 ppm on MaxQuant DDA rows — inferred, flagged.** `parameters.txt`
lists tolerances per analyzer type (`FTMS 20 ppm`, `ITMS 0.5 Da`, **`TOF 40 ppm`**, `Unknown 20 ppm`);
MaxQuant selects the branch from the raw file's analyzer, which for timsTOF data is TOF. The value is
read from the deposited file; the *branch selection* is my inference. The paper says only
"searched as default for TIMS-DDA data".

## Traps encountered

1. **OLS smart mode returned the wrong concept for `thymidine`** — a confident single "exact" hit on
   **`Thymidine Kinase, Cytosolic` (`NCIT:C38512`)**, an enzyme, not the nucleoside. `mode="fuzzy"`
   surfaced the correct **`Thymidine` `NCIT:C880`** at rank 2. A live instance of the documented
   smart-mode trap, on a term nobody would think to double-check.
2. **`SampleType="Blank"` inside every single-cell `SampleInfo.xml`.** The HyStar sample table records
   `SampleType = "Blank"` for run `…_1Cell_HeLa_UB_28_…` — a default field, not a claim. Trusting it
   would have discarded the entire single-cell set as blanks. The real blanks are named `0cell`/`0ng`.
3. **Filename dates are not acquisition dates.** `20201009_…_3873.d` carries
   `AcquisitionDateTime = 2020-10-10T13:13`. The filename date is the queue/sample-list date. This is
   why `comment[acquisition date]` (optional) is omitted rather than filled from filenames.
4. **Per-cell numbering repeats across EvoTip boxes.** `NB_01` exists on both 20201009 (tip `S3-G2`)
   and 20201010 (tip `S5-B2`) — 8 such collisions. The slot is a deterministic function of the index
   (`G2..G12` = 1..11), and the two days used **different boxes** (rows G–H in slot S3; rows B–G in
   slot S5), so these are distinct tips holding distinct cells, not re-injections. Identifiers are
   therefore date-scoped (`NB_20201009_001`), giving 434 unique cells. Naively keying on
   condition+index would have silently merged 8 cells. **This is an inference from tip geometry** —
   the deposition cannot prove it; a reviewer should challenge it.
5. The 6 library-generating DDA runs (`…_200ng_SCPHeLa_DDA_01..06`) referenced by
   `MSFRAGGER_Output_Library.zip` are **not deposited** — only their `pepXML`. 520 raw runs are
   deposited; 526 were acquired.

**One warning, justified and left in place:**
`WARNING: Invalid value 'G1/S' - must be one of the allowed values` (41 TB rows).
`single-cell/1.0.0` allows `[G1, S, G2, G2/M, M, G0, not determined]` — it has `G2/M` but **no
`G1/S`**, an asymmetric gap in the enum. The paper's design names the G1/S transition as one of its
four target stages. The alternatives are `S` (false — a thymidine block arrests *at* the boundary,
not in S phase) or `not determined` (discards the study's design). The enum's `error_level` is
`warning`, so the truthful value is kept. Recorded in `annotations/BLOCKED.md` as a spec gap.

**`parse_sdrf` exiting 0 proves well-formedness, never truth.** Every finding in this report —
the paper-vs-`summary.txt` modification conflict, timsTOF SCP vs Pro, HeLa vs HeLa-S3, the 8 colliding
cell indices, `SampleType="Blank"` — passes the validator cleanly in either direction.
