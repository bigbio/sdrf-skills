## Study and publication

- **Dataset:** PXD040455 — *HyperSCP: Combining Isotopic and Isobaric Labeling for Higher Throughput
  Single-Cell Proteomics.*
- **Publication:** Liang Y, Truong T, Saxton AJ, Boekweg H, Payne SH, Van Ry PM, Kelly RT. *Anal Chem*
  2023, 95(20):8020-8027. PMID **37167627**, PMCID **PMC10246935**, DOI 10.1021/acs.analchem.3c00906.
  Not in the PMC OA subset; full text recovered via the PMC BioC text-mining API and the submitter
  protocols in PRIDE.
- **Method (hyperSCP):** each nested well of a custom nanowell chip received **14 SILAC-light + 14 SILAC-heavy
  single cells + 2 PBS droplets**, then TMTpro labeling. SILAC (isotopic, 2-plex) × TMTpro (isobaric)
  multiplies throughput: one raw file resolves up to 28 single cells, plus carrier / reference / negative
  channels. Instrument Orbitrap Exploris 480, DDA, HCD, 35% NCE. Four cell lines across four chips.

## The Table S1 channel→sample map and how it was verified

**Primary source:** the paper's Table S1 (`Table_S1_Cells_in_Channels.xlsx`, PMC supplement
`NIHMS1901450-supplement-...`). PMC serves it behind a proof-of-work challenge; I solved the SHA-256 POW
and downloaded the genuine XLSX (19,563 bytes, valid Office Open XML), not the anti-bot HTML shell.

The paper's own R pipeline (github.com/RTKlab-BYU/HyperSCP) documents the exact semantics, which I used to
decode the table:
- Table S1 sheet **"2_cells in channles-hyperSCP"** is keyed by **field number** (`Location` = F1…F35).
  The **same field layout applies to every chip**; the chip only maps the abstract tokens to cell lines.
- Columns `126…135N` = the **SILAC-light** search; columns `SILAC_126…SILAC_135N` = the **SILAC-heavy**
  search. Each single cell is one (TMTpro channel × SILAC state).
- Token semantics: `Boost` = carrier (channel 126), `Reference` (channel 134N), `NotUsed` (channel 127C),
  `Control` = a PBS negative-control droplet (**not a cell**), `Cell_1`/`Cell_2` = single cells.
- Chip→cell-line (from `actual_cell()` in the R code): **Chip1 & Chip2 → Cell_1=HeLa, Cell_2=K562;
  Chip3 → HeLa/A549; Chip4 → HFL1/A549** — consistent with the raw filenames (`Chip3_A549HeLa_*` etc.).

**Verification result (script, not eyeball):** I rebuilt the ground-truth map for all 42 deposited chip
raw files directly from Table S1 and compared it cell-by-cell to the existing SDRF:
- **42 / 42 files match exactly.** 0 wrong cell-line assignments, 0 missing cells, 0 extra cells.
- Row accounting reproduced independently: **40 files × 28 + 2 files × 29 = 1178.** The two 29-cell files are
  **Chip2_F21 and Chip4_F21**, where Table S1 places only **one** `Control` (one PBS droplet) instead of two,
  so 29 channel-slots are single cells.
- Single-cell channels are the 15 usable TMTpro channels (all except 126, 127C, 134N) × 2 SILAC = 30 slots,
  minus the PBS `Control` slots → 28 (or 29) cells per file.

**Carrier / reference / negative handling (verified):**
- **Carrier** (channel 126, a 10 ng light+heavy HeLa/A549 booster) and **reference** (channel 134N, 0.5 ng)
  are **not annotated as single-cell rows** — they are bulk standards, captured only as
  `comment[carrier channel]` / `comment[reference channel]` metadata. This is the correct SCP representation
  (a carrier is `sample type = standard`, never a single cell); here it is recorded as a comment rather than
  a separate row, so no carrier row is mislabeled as a cell.
- The R pipeline sets carrier presence by `Field <= 21 → 10 ng carrier`, `Field > 21 → none`
  ("for carrier-free samples: no 126 and 127C"). The SDRF encodes this as
  `comment[carrier channel] = TMT126` for the 28 files with field ≤ 21 and `not applicable` for the 14 files
  with field > 21 (Chip2 ×5, Chip3 ×5, Chip4 ×4). **Verified: 0 carrier mismatches** across all 42 files.
- **PBS `Control` and `NotUsed` channels are excluded entirely** (no rows), so no PBS/blank droplet is given
  a fabricated cell identity. `comment[reference channel] = TMT134N` on all rows.

**Deposited vs annotated reconciliation:** PRIDE `files/all` lists **46 raw files** (asserted: every entry's
`projectAccessions` contains PXD040455). **42** are the hyperSCP single-cell chip runs → fully annotated
(1178 rows). The **4** remaining (`10ng_A549_H/L_...`, `10ng_HeLa_H/L_...`) are **bulk 10 ng digest
labeling/coverage-characterization standards** (the abstract's "labeling efficiency and achievable proteome
coverage were characterized"), not single cells and with no channel→single-cell map — **deliberately not
included** in this single-cell SDRF. Table S1's second sheet ("TMTpro only") describes a non-SILAC arm that
does not correspond to the deposited SILAC chip runs.

## SILAC × TMTpro encoding (per-row)

- `comment[label]` = the TMTpro reporter channel (the isobaric dimension).
- The SILAC (isotopic) dimension is carried in **`comment[modification parameters]`**: heavy rows add
  `Label:13C(6)15N(2)` (**UNIMOD:259**, +8.014) on K and `Label:13C(6)15N(4)` (**UNIMOD:267**, +10.008) on R,
  both Fixed; light rows leave those two columns `not applicable`. This matches the data-processing protocol
  exactly (heavy K search mod = TMTpro 304.207 + 8.014 = 312.221; heavy R = +10.008), and the light/heavy
  state is also carried in the `source name`/`cell identifier` suffix (`_light` / `_heavy`).
  Split: **590 light + 588 heavy** rows.
- Static mods on all rows: **TMTpro** (UNIMOD:2016) on K and on Any N-term; **Carbamidomethyl** (UNIMOD:4)
  on C. Variable: **Oxidation** (UNIMOD:35) on M; **Deamidated** (UNIMOD:7) on N. Cleavage: **Trypsin**
  (MS:1001251) + **Lys-C** (MS:1001309). Precursor 10 ppm, fragment 0.6 Da — all verbatim from the paper.

**Carbamidomethyl is legitimate here (checked per corpus rule):** unlike many SCP protocols, hyperSCP
performs explicit reduction + alkylation — "5 mM TCEP … 45 mM CAM" (chloroacetamide) in the sample protocol,
and the search sets carbamidomethyl (+57.021) as a static Cys mod. `comment[reduction reagent] = TCEP`,
`comment[alkylation reagent] = 2-chloroacetamide`.

## Fixes I made to the existing SDRF

1. **K562 organism part: `bone marrow (UBERON:0002371)` → `pleural effusion (UBERON:0000175)`** (253 rows).
   Cellosaurus CVCL_0004 records K-562's derived-from site as **Pleural effusion** (UBERON:0000175); the
   line was established from the pleural fluid of a CML patient in blast crisis. "Bone marrow" was the prior
   agent's error (the disease's typical site, not the cell line's derivation site). Confirmed live in
   Cellosaurus and OLS.
2. **Collision energy: `35` → `35% NCE`** (all 1178 rows). The bare number failed the `ms-proteomics`
   pattern (`{value} {unit}`, unit NCE/eV). The paper states "35% normalized HCD collision energy", so the
   value was right and only the unit was missing — now primary-source-verified, not guessed.

**A trap I did NOT fall into:** the task brief suggested HFL1 = `CVCL_3495`. Cellosaurus shows **CVCL_3495 is
CA-HPV-10, a prostate carcinoma line**; HFL1's real accession is **CVCL_0298**, which is what the SDRF
already had. I left it unchanged. (Verified live.)

## Values left `not available` / `not applicable` — and why

- `culture medium`, `passage number` = **not available** — not reported per cell line in paper/PRIDE.
- `characteristics[cell type]` for K562 = **not available** — no CL term stated; K562 is an
  erythroleukemia/lymphoblast line but the paper does not assign a cell type. (HeLa/A549 = epithelial cell;
  HFL1 = fibroblast of lung, both supported.)
- `characteristics[ancestry category]` for K562 and A549 = **not available** — Cellosaurus does not give a
  confident population for these; only HeLa (African American) and HFL1 (European) are supported.
- HFL1 `developmental stage` and `age` = **not available** — Cellosaurus states HFL1 is **fetal lung**
  (donor age 16 fetal weeks), so the donor stage is genuinely *fetal*, but OLS returned no clean SDRF
  developmental-stage term for "fetal" (smart search fell back to "late embryonic stage"), so rather than
  guess a term I left it `not available`. **Flagged for the reviewer** (see below).
- `comment[carrier channel]` = **not applicable** on the 14 carrier-free files (field > 21) — there is no
  carrier channel in those runs.
- Two `comment[modification parameters]` columns = **not applicable** on light rows — the SILAC heavy labels
  do not apply to light cells.

## Hardest judgment calls — please attack these

1. **PBS `Control` droplets excluded rather than annotated as blank rows.** Each field has 1–2 PBS negative
   droplets occupying real TMTpro channel-slots. I kept the prior agent's choice to omit them (no row) rather
   than emit rows with a non-cell `sample type`. Alternative view: annotate them as `sample type = not
   applicable`/blank with `cells per well = 0`. I chose exclusion to avoid fabricating cell identity and
   because the single-cell template's row model is one-row-per-single-cell; the count reconciliation is fully
   documented. Reviewer may prefer explicit blank rows.
2. **Carrier/reference as comments, not rows.** No row exists for the 126 carrier (10 ng bulk HeLa/A549
   standard) or the 134N reference (0.5 ng). This is the common SCP convention here, but a reviewer wanting a
   `sample type = standard` carrier row would see it as missing.
3. **SILAC encoded via modifications + name suffix, not `comment[label]`.** `comment[label]` holds only the
   TMTpro channel; the light/heavy (isotopic) axis is expressed through UNIMOD:259/267 mods and the
   `_light`/`_heavy` source-name suffix. This is validator-clean and faithful to how the data were searched,
   but there is no single ontology column that says "SILAC heavy channel" — a reviewer may want that surfaced
   more explicitly.
4. **HFL1 developmental stage left `not available` despite known fetal origin** (see above) — a reviewer who
   accepts an HsapDv/EFO fetal-stage term may want it filled.
5. **4 bulk 10 ng runs excluded** from this single-cell SDRF. They are deposited and have samples (bulk
   HeLa/A549 digest, SILAC light/heavy), so a strict "annotate every deposited run" reading would want a
   separate bulk arm; I judged them out of scope for the single-cell deliverable and documented them.
