## Templates chosen and why — and the MIXED-ACQUISITION decision

`comment[sdrf template]` declares **four**: **ms-proteomics v1.1.0**, **human v1.1.0**, **cell-lines v1.1.0**, **single-cell v1.0.0**.

**dia-acquisition was deliberately OMITTED.** This deposition mixes 128 DIA rows (arms A+B) with **10 DDA rows** (arm C). The `dia-acquisition` template (v1.1.0) *hard-restricts* `comment[proteomics data acquisition method]` to the single value `Data-independent acquisition` (enforced enum in the template YAML). Declaring it makes `parse_sdrf` reject every DDA row:

```
ERROR: Column 'comment[proteomics data acquisition method]' has multiple unique values: Data-independent acquisition, Data-dependent acquisition
ERROR: Invalid value 'Data-dependent acquisition' - must be one of the allowed values
```

Per the task's own guidance ("omit dia-acquisition and leave DIA-specific comments off"), I dropped dia-acquisition **and** its four DIA-specific columns (`scan window lower/upper limit`, `isolation window width`, `dia method`). Under the remaining `ms-proteomics` template the acquisition column is validated against the **PRIDE ontology** (not a fixed enum), so both `Data-independent acquisition` (PRIDE:0000450) and `Data-dependent acquisition` (PRIDE:0000627) pass, per row. The DDA arm is therefore **not forced onto DIA parameters**; its acquisition method is honestly `Data-dependent acquisition`.
- Trade-off accepted: the DIA scan-window parameters are no longer structured columns. They are recorded here instead — **DIA arms (A+B): full-MS 380–980 m/z, 4 Th isolation window, 6 ms max IT, narrow-window (n)DIA, HCD 25% NCE.** (This differs from the sibling `PXD054445`, which is pure-DIA and so could keep dia-acquisition + those columns.)
- The alternative (splitting into two files) was rejected because the deliverable is a single `PXD056327.sdrf.tsv`.

`single-cell` is declared because arm B (96/138 rows) is true single cells; it licenses `single cell isolation protocol`, `cell identifier`, `cells per well`, `sample type`. Pooled arms (A, C) set those to `not applicable`. `cell-lines` licenses `cell line`, `cellosaurus *`, `culture medium`, etc. Column licensing was resolved with `spec/scripts/resolve_templates.py`; every column used is licensed by a declared template.

Gradient is not an SDRF column, so this does not affect any cell; flagged for completeness (raw wins).

## The judgement calls I most want a reviewer to attack

1. **`comment[label]` = `label free sample` (MS:1002038) for the TMTproZero DDA arm C.** TMTproZero is a chemical mass tag, so calling these rows "label free" is arguable. My reasoning: TMTproZero is a *single, non-isobaric* reagent — there is **no reporter-ion multiplexing and no channel→sample map**, each file is one sample, and the search treats the tag as a **variable modification** (captured fully in the mod columns), not a quantitative labeling scheme. There is no SDRF/PRIDE label term for a mono-plex TMT-zero tag; `label free sample` is the honest description of the (non-multiplexed) quantification. A reviewer may prefer a TMT label term — but every such term implies isobaric channels that do not exist here.
2. **Omitting dia-acquisition + its columns** (the mixed-acquisition handling above) vs. splitting the file.
3. **One-Tip `cells per well` = `not applicable`** despite the counts being known (1000/3000) — I treat an Evotip as not-a-well; a reviewer could argue for recording the integer.
4. **`factor value[storage condition]` = `not applicable` for arms A/C**, and encoding the storage variable as a free-text factor value at all (no ontology backing).
