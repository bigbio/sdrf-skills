## Study

**autoPOTS** (Automated Preparation in One pot for Trace Samples): a low-input proteomics workflow
built entirely from commercial instrumentation — an Opentrons OT-2 pipetting robot for one-pot
preparation in a 384-well plate, plus an UltiMate WPS-3000 autosampler modified with a 10-port valve
to drive a 30 µm i.d. nanoLC column at ~40 nL/min. Label-free throughout, one run per well.

Two arms: (a) a HeLa dilution series (0–500 cells) benchmarking coverage against the authors' earlier
nanoPOTS platform; (b) a clinical-feasibility arm profiling FACS-sorted B and T lymphocytes from one
healthy donor.

## The screen's `publication=unclear` is corrected — a paper exists and was read in full

PRIDE's `publications` field is an **empty list**, so no DOI existed in the PRIDE record to resolve.
This is the same failure mode as `PXD019515`, and it was resolved the same way: the deposition
*title* is the article title verbatim. A Europe PMC free-text search for `PXD021882` returns
PMC8140400, whose own Data Processing section states *"deposited to the ProteomeXchange Consortium
via the PRIDE partner repository with the dataset identifier PXD021882"*. The link is bidirectional
and certain.

**`is_open_access` was unreliable exactly as the brief warns.** Europe PMC reports `OA: N` and its
`supplementaryFiles` endpoint answers *"Article with id PMC8140400 is not open access one"*.
`get_full_text_article` returns **HTTP 404 (not in OA subset)** and `get_pdf_by_unpaywall` fails with
`Download failed: HTTP 404` — while simultaneously reporting `oa_status: green`. That contradiction
was the tell. The article is a **PMC author manuscript** (NIHMS1703252) and its full text is served
as HTML at `pmc.ncbi.nlm.nih.gov/articles/PMC8140400/`. It was fetched and parsed there.

**So PRIDE protocol text was *not* the only evidence.** The peer-reviewed Methods were read in full
and outrank PRIDE throughout. Beyond that, the deposited search files turned out to be a better
source than either — see *Modifications* and *Tolerances*.

## Templates

`ms-proteomics v1.1.0`, `human v1.1.0`, `single-cell v1.0.0`. No exclusivity conflict under
symmetric closure (computed, not assumed: `human` excludes only `vertebrates`/`invertebrates`/
`plants`/`metaproteomics`).

**`cell-lines` was deliberately NOT declared — the central decision in this file.** I re-derived the
constraint from the resolved template rather than inheriting it: `characteristics[cell line]` is
`required` in `cell-lines/1.1.0` with **both** `allow_not_applicable` and `allow_not_available`
`false`.

This deposition is a **mixed cohort**. 16 of 37 rows — 10 primary lymphocytes and 6 supernatant
blanks — have no cell line and **no legal value exists for them**. Declaring `cell-lines` would mean
asserting a cell line for 16 rows that have none. The alternative (declare it, annotate only the 21
HeLa cell rows) would discard the paper's entire clinical result (Fig. 5, the B-vs-T comparison) plus
both blank groups. Both rejected; `cell-lines` dropped.

**What this costs:** `CVCL_0030` has no dedicated column. HeLa identity survives as
`characteristics[cell type]` = `NT=HeLa cell;AC=CLO:0003684` — legal, since that column's resolved
validator explicitly allows `clo` — and as `characteristics[material type]` = `cell line`. This
follows `PXD019515` deliberately; `PXD052416` used `epithelial cell` instead, which was right *there*
because that file could declare `cell-lines` and put HeLa in its proper column.

This is the **fifth** dataset to hit this wall; recorded in `annotations/BLOCKED.md`.

## Key decisions and evidence

**Modifications come from the deposited search files, not from "default settings".** The paper says
only *"All other settings were the default"* (MaxQuant) and *"default settings other than enabling
quantification"* (MSFragger) — which would have forced me to infer mods from software defaults. That
inference was unnecessary: `summary.txt` (MaxQuant 1.6.7.0) states per run
`Fixed modifications = Carbamidomethyl (C)`, `Variable modifications = Oxidation (M);Acetyl (Protein
N-term)`, and all three MSFragger `pep.xml` headers independently declare the identical set
(`C +57.0215` fixed, `M +15.9949` variable, protein N-term `+42.0106` variable). Two engines, three
searches, one answer. Recorded as:

- `NT=Carbamidomethyl;AC=UNIMOD:4;TA=C;MT=Fixed` — corroborated by the IAA alkylation step
- `NT=Oxidation;AC=UNIMOD:35;TA=M;MT=Variable`
- `NT=Acetyl;AC=UNIMOD:1;PP=Protein N-term;MT=Variable`

`UNIMOD:1` = Acetyl verified live (not swapped with `UNIMOD:21` = Phospho). The N-terminal position
is in `PP=`, not `TA=`. PRIDE's `modifications` field lists only *"iodoacetamide derivatized residue"*
— i.e. Carbamidomethyl alone — and is incomplete rather than contradictory; the deposited search
files were followed.

**Tolerances are per-row, because FragPipe optimized them per search group.** All three MSFragger
searches ran with `calibrate_mass=2` (mass calibration **and parameter optimization**), so "default
settings" wrote *different* fragment tolerances into each pep.xml:

| search | runs | engine | fragment tol |
|---|---|---|---|
| `MSFragger_HeLa_1_500_combined` | 15 micromanipulation HeLa | 3.1.1 | **10 ppm** |
| `MSFragger_HeLaCell_1_500_FACS_combined` | 12 FACS HeLa + blanks | 3.0 | **15 ppm** |
| `MSFragger_FACS_B_T_combined` | 10 lymphocytes | 3.1.1 | **5 ppm** |

Each raw file belongs to exactly one search, so every row gets its true value. A single
whole-file constant would have been wrong for 22 of 37 rows and would have passed validation.
`comment[precursor mass tolerance]` = `20 ppm` (`precursor_true_tolerance`) on all rows — identical
across all three searches.

**Which search does the SDRF describe? MSFragger.** MaxQuant covers only the 15 micromanipulation
HeLa runs and exists solely to compare against the authors' prior nanoPOTS work; MSFragger covers all
37 runs and produced the reported results (Figs. 4, 5). Noted because MaxQuant's `parameters.txt`
records `MS/MS tol. (FTMS) = 20 ppm`, which disagrees with all three MSFragger fragment tolerances.
Following MaxQuant would put one number on rows the MaxQuant search never touched.

**Parental HeLa is correct here — the `PXD052416` HeLa-S3 trap does not apply.** That dataset's HeLa
was a *commercial digest standard* (Thermo cat. 88328), which is manufactured from HeLa-S3. Here the
paper says *"HeLa cells were obtained from ATCC (Manassas, VA) and cultured at 37 °C..."* — live
cultured cells from ATCC, i.e. HeLa CCL-2 = `CVCL_0030`. Checked rather than assumed.

**The HeLa OLS trap was hit and avoided.** `mode="fuzzy"` on `HeLa` in **CLO** does not return the
parental line at all in its top 6 — it leads with `HeLa-MAGI-CCR5` (CLO:0037219). Querying `"HeLa
cell"` in `mode="exact"` returns `CLO:0003684` as the exact hit. In EFO, fuzzy `HeLa` returns
`EFO:0001185` first but with `HEp-2` (EFO:0006438) in the same list — the hit smart mode would have
returned confidently.

**HeLa donor demographics are Cellosaurus-sourced, not paper-sourced.** `age=30Y6M`, `sex=female`,
`ancestry=African American` (HANCESTRO:0568) come from the live Cellosaurus record for `CVCL_0030`.
The paper states none. These columns are licensed by `human`, so dropping `cell-lines` does not
un-license them. `organism part` = `uterine cervix` (UBERON:0000002).

**Disease.** HeLa → `cervical adenocarcinoma` (MONDO:0005153). Cellosaurus asserts the finer
`NCIT:C27677` "HPV-related endocervical adenocarcinoma", but TERMS.tsv's `values` lists
`MONDO, EFO, DOID, PATO` in preference order and MONDO has no HPV-related cervical term. The HPV
sub-claim is dropped rather than smuggled in. Lymphocytes → `normal` (PATO:0000461), directly stated:
*"blood was drawn from a healthy male donor"*.

**Cleavage agents — stated, not inferred.** `Trypsin` (MS:1001251) + `Lys-C` (MS:1001309) on all 37
rows. Unlike `PXD019515`, where Lys-C was inferred from a reagent list, the paper is explicit:
*"proteins were predigested using 1 µL of lys-C for 3 h at 37 °C and then digested by adding 1 µL of
trypsin"*. The searches specified trypsin only, but this column describes **digestion**, not the
search.

**Donor structure — a real confounder, made explicit.** All 10 lymphocyte runs come from **one**
donor (`characteristics[individual]` = `Subject1`; the paper says "a healthy male donor", singular,
IRB X19045). The headline B-vs-T comparison is therefore n=1 donor, 5 wells per cell type. That is
visible in the SDRF rather than buried. Same shape as `PXD019515`'s single spinal donor.

**Replicate structure.** Each well is a distinct sample and a distinct biological replicate,
numbered within its group. `technical replicate = 1` and `fraction identifier = 1` throughout — no
fractionation, no repeat injection anywhere.

**Factors.** Two, because the study has two arms: `factor value[cells per well]` (the HeLa dilution
series, Fig. 4) and `factor value[cell type]` (B vs T, Fig. 5). Both mirror their characteristics
column exactly (37/37 verified).

**`organism part` for lymphocytes = `blood` (UBERON:0000178), not `venous blood`.** Blood drawn into
an EDTA tube at a student health center is almost certainly venous (UBERON:0013756 exists), but the
paper never says "venous". The broader stated term was preferred over the narrower inferred one; the
cell type column carries the real information.

## Contestable calls, flagged for the reviewer

1. **`single cell isolation protocol` = `manual picking` for the 150- and 500-cell wells.** Those
   wells received a *measured suspension volume* (150/500 nL of 10⁶ cells/mL) through the same
   micromanipulation capillary — not individually picked cells. The enum
   (`FACS, cellenONE, microfluidics, laser capture microdissection, manual picking, nanoPOTS, droplet
   microfluidics, acoustic droplet ejection`) has no member for "manual bulk aliquot". `manual picking`
   preserves the micromanipulation-vs-FACS axis, which is a genuine experimental variable in this
   study (Fig. S6 compares them); `not applicable` would erase it. This is the weakest claim in the file.
2. **`cells per well` = 145 for the lymphocytes is the *nominal* target, not a measured count.** The
   sorter was set to 145; a bead test gave ~89% efficiency (129/145); the abstract itself says
   "~130 ... lymphocytes". Actual per-well counts were **never measured for cells** — only for beads.
   145 is what was sorted and what the file names record. The ~130 figure is an efficiency-derived
   estimate, not a measurement, so it was not written into the SDRF.
3. **HeLa `cells per well` is nominal too.** The paper says counts were verified by photomicrograph
   and reports them in **Table S3** — which I could not retrieve: NCBI serves the supplement behind a
   JavaScript proof-of-work anti-bot page (the "publisher anti-bot HTML" the brief warns about), and
   Europe PMC refuses it as non-OA. If Table S3 is obtained, `characteristics[cells per well]` for the
   1/10-cell wells should be re-checked against it — a well labelled `1cell` may hold 0 or 2.
4. **`cell type = HeLa cell (CLO:0003684)`** — the deliberate divergence from `PXD052416`'s
   `epithelial cell`, inherited from `PXD019515`. Defensible (CLO is validator-allowed) but contestable.
5. **Precursor tolerance nuance.** `precursor_true_tolerance` is 20 ppm, but
   `precursor_mass_lower/upper` is ±50 ppm in all three searches. I recorded 20 ppm as the effective
   optimized tolerance; a reviewer may prefer 50 ppm as the search window.
6. **MaxQuant/paper conflict, not SDRF-relevant but noted:** `parameters.txt` says
   `Match between runs = True`; the paper says *"Match between runs was not used for MaxQuant or
   MSFragger analysis."* No SDRF column carries this, so it changed nothing here — but it means the
   deposited `parameters.txt` and the manuscript disagree about the MaxQuant run.

**One warning, justified:**
`Term: NT=T cell;AC=CL:0000084 in column 'characteristics[cell type]', is not found in the given
ontology list cl;bto;clo`

This is a `parse_sdrf` lookup artifact, not a defect in the file. `CL:0000084` was verified twice
live — via `searchClasses` (exact single hit, label `T cell`) and directly against the OLS4 REST API
(`label: T cell`, `obo_id: CL:0000084`, `is_obsolete: false`, synonyms `T lymphocyte`/`T-cell`/…).
`B cell` (`CL:0000236`) in the same column with the same format does **not** warn. The warning
**reproduces across runs**, so it is a systematic gap in the validator's bundled CL lookup rather
than a transient network miss. Per the skill's own guidance, the accession was verified rather than
the term rewritten; renaming a correct term to silence a validator would be the actual error.
